This is the optional phase. Everything before this post — the blog, videos, tweets, themes, multilingual support — works without a single API call. The site is fully static, deployed as plain HTML/CSS/JS. But I wanted to add one more layer of interactivity: metrics and a like button. That requires a backend.

This phase is marked as optional because it adds complexity (a database, API routes, runtime data fetching) that a personal site does not strictly need. If you just want a blog, skip this entirely. But if you want to see how to connect a Next.js frontend to a database and build interactive features, read on.

Prisma Setup and Database Schema

I chose Prisma for the database layer. It is a type-safe ORM that generates TypeScript types from your schema, which means your database queries get full autocomplete and compile-time error checking. The setup is minimal.

The Schema

The schema is simple — just two models:

generator client {
  provider = "prisma-client-js"
}
 
datasource db {
  provider = "sqlite"
  url      = env("DATABASE_URL")
}
 
model PostMetric {
  id        String @id @default(cuid())
  slug      String @unique
  views     Int    @default(0)
  likes     Int    @default(0)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}
 
model PostLike {
  id        String @id @default(cuid())
  slug      String
  sessionId String
  createdAt DateTime @default(now())
 
  @@unique([slug, sessionId])
}

PostMetric stores aggregate counts per post. PostLike stores individual like records, keyed by a session ID (a salted hash of the user's IP address). The @@unique constraint on [slug, sessionId] means one session can only like a post once.

SQLite for Development

For development, I use SQLite (DATABASE_URL="file:./dev.db"). It requires no setup — just a file on disk. For production, you would swap to MySQL or Postgres by changing the provider and url in the schema. The schema itself is portable — no database-specific features.

The Prisma Client

A singleton pattern prevents creating multiple database connections in development:

// lib/prisma.ts
import { PrismaClient } from "@prisma/client"
 
const globalForPrisma = globalThis as unknown as { prisma: PrismaClient }
 
export const prisma = globalForPrisma.prisma || new PrismaClient()
 
if (process.env.NODE_ENV !== "production") globalForPrisma.prisma = prisma

This is a common Next.js pattern. In development, hot reloading would create a new PrismaClient on every save, eventually exhausting database connections. The globalThis trick reuses the same client instance across reloads.

API Routes for Views and Likes

The Views API

The views endpoint at pages/api/views/[slug].ts increments a counter each time a post is viewed:

export default async function handler(req, res) {
  const slug = z.string().parse(req.query.slug)
 
  if (req.method === "POST") {
    // Increment view count
    await prisma.postMetric.upsert({
      where: { slug },
      update: { views: { increment: 1 } },
      create: { slug, views: 1 },
    })
    return res.json({ ok: true })
  }
 
  if (req.method === "GET") {
    const metric = await prisma.postMetric.findUnique({ where: { slug } })
    return res.json({ views: metric?.views ?? 0 })
  }
}

The upsert is key — it either creates a new record (first view) or increments the existing one. The zod validation ensures the slug is a clean string.

The Likes API

The likes endpoint is more complex because it needs to track individual sessions:

export default async function handler(req, res) {
  const slug = z.string().parse(req.query.slug)
  const sessionId = getSessionId(req) // salted hash of IP
 
  if (req.method === "POST") {
    // Check if already liked
    const existing = await prisma.postLike.findUnique({
      where: { slug_sessionId: { slug, sessionId } },
    })
 
    if (existing) {
      return res.json({ likes: await getLikeCount(slug), liked: true })
    }
 
    // Create like and increment count
    await prisma.$transaction([
      prisma.postLike.create({ data: { slug, sessionId } }),
      prisma.postMetric.upsert({
        where: { slug },
        update: { likes: { increment: 1 } },
        create: { slug, likes: 1 },
      }),
    ])
 
    return res.json({ likes: await getLikeCount(slug), liked: true })
  }
}

The session ID is a salted MD5 hash of the user's IP address (x-forwarded-for header). This is not foolproof — a determined user could change their IP — but it prevents casual like inflation.

Caching

Both endpoints set Cache-Control headers for CDN caching:

res.setHeader("Cache-Control", "public, s-maxage=60, stale-while-revalidate=300")

This means Vercel's edge cache serves the response for 60 seconds, then revalidates in the background for another 300 seconds. This reduces database load significantly.

PostMetrics Component

The PostMetrics component displays view and like counts on the blog detail page. It fetches data from the API routes using SWR:

export function PostMetrics({ slug }: { slug: string }) {
  const { data } = useSWR(`/api/views/${slug}`, fetcher, {
    revalidateOnFocus: false,
  })
 
  return (
    <div className="text-muted-foreground flex items-center space-x-4 text-base">
      <InlineMetric stat={data?.views ?? 0} label="views" />
      <span className="text-foreground/30">&middot;</span>
      <InlineMetric stat={data?.likes ?? 0} label="likes" />
    </div>
  )
}

The InlineMetric component animates number transitions — when the count changes, the digits slide up like an odometer. It is a small detail that makes the metrics feel alive.

The Like Button

This was the most fun part of the entire project. The like button is an interactive SVG heart that fills up, shows emoji reactions, and persists to the database.

The Heart SVG

The heart is an SVG with two rectangles masked by a heart shape:

<svg viewBox="0 0 400 400">
  <defs>
    <mask id="heart-mask">
      <path d="M200 350..." fill="white" />
    </mask>
  </defs>
 
  {/* Background rectangle (gray) */}
  <rect fill="#666" mask="url(#heart-mask)" width="400" height="400" />
 
  {/* Fill rectangle (gradient, animated) */}
  <rect
    fill="url(#like-gradient)"
    mask="url(#heart-mask)"
    width="400"
    height="400"
    style={{ transform: `translateY(${fillY}px)` }}
  />
</svg>

The gradient rectangle starts below the mask and translates upward as the user likes the post. At 0 likes, it is hidden. At 1 like, it fills 33%. At 3 likes (the maximum), it fills completely.

The Animation

When the user clicks, several things happen simultaneously:

  1. The heart scales up and back (a "pop" effect)
  2. The gradient fill translates upward
  3. An emoji floats up and fades out
  4. The like count increments
const handleClick = async () => {
  // Optimistic UI — update immediately
  setLikes((prev) => prev + 1)
  setShowEmoji(true)
 
  // Persist to database
  const res = await fetch(`/api/likes/${slug}`, { method: "POST" })
  const data = await res.json()
 
  // Reconcile with server
  setLikes(data.likes)
}

The optimistic update is important — the count changes instantly, and the database call happens in the background. If the call fails, the count reverts. SWR handles this reconciliation pattern well.

The Confetti

I added a small confetti burst when the user likes the post. It uses CSS animations — a few colored circles that fly outward and fade:

@keyframes confetti {
  0% {
    opacity: 1;
    transform: translate(0, 0) scale(1);
  }
  100% {
    opacity: 0;
    transform: translate(var(--x), var(--y)) scale(0);
  }
}

Each confetti particle gets random --x and --y values via inline styles, so they fly in different directions. The effect is subtle — 6-8 particles, 500ms duration. Not a full Josh Comeau confetti cannon, but enough to make the interaction feel rewarding.

Integration with the Blog Page

The like button sits below the post title, next to the metrics:

<div className="flex items-center space-x-4">
  <PostMetrics slug={post.slug} />
  <LikeButton slug={post.slug} />
</div>

The metrics show aggregate counts. The like button is the interactive element. Together they give each post a sense of engagement — even on a personal blog with a small audience.

Wrapping Up

This phase added the backend layer — a database, API routes, metrics, and an interactive like button. The site now has a full stack: static content at build time, dynamic data at request time.

But remember — this entire phase is optional. The site was complete before this. The metrics and likes are polish, not core functionality. If you are building your own site, ship the content first. Add the interactive bits later, when you have an audience that will use them.
